# ContextWeaver adopters

This file records **genuine independent use**, not GitHub popularity.

A star, fork, package download, clone, synthetic demo run, or maintainer-operated proof is not enough to appear here. Public entries must be self-reported by the adopter or explicitly approved by them.

## Status definitions

- **evaluating** — testing ContextWeaver against real or representative capability sources.
- **integrated** — ContextWeaver is used in a genuine project or delivery workflow.
- **retained** — the genuine integration is still active after approximately 30 days.
- **former** — an evaluation/integration was removed or abandoned; the reason is valuable product evidence when the adopter is willing to share it.

These are evidence states, not prestige levels.

## Submit your use case

Use the **Adoption / evaluation report** issue form if you are willing to describe how you evaluated or integrated ContextWeaver. You may:

- identify your project/organization or submit as `anonymous`;
- keep proprietary capability names, schemas, prompts and infrastructure private;
- choose whether you permit a public entry in this file;
- optionally allow a ~7-day / ~30-day follow-up so the project can distinguish a successful demo from retained use.

The maintainer will not infer adoption from public activity or turn casual positive comments into an adopter claim.

## Case-study quality bar

A public case study should explain:

1. the pre-existing problem/workaround;
2. the simpler alternatives considered (for example provider-native tool search, gateway-only configuration, ordinary config/version control, or simple retrieval);
3. what ContextWeaver was actually used for;
4. the observable/measurable result;
5. limitations and operational cost;
6. whether the integration persisted.

Negative evidence is welcome. A former adopter who found that a native provider feature was sufficient teaches the project more than an unqualified testimonial.

## Privacy and evidence policy

- Public listing requires explicit permission or an adopter-owned pull request.
- Anonymized product-validation records should use cohort/project identifiers rather than personal information where possible.
- Never publish customer/proprietary capability definitions or internal metrics without permission.
- Never pay, trade favors, solicit stars/votes, or coordinate engagement in exchange for adoption/case-study participation.
- Product decisions use the evidence model in issues #758, #840, #658 and #551.
